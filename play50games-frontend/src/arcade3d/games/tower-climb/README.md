### What a new game copies from here

- Use robot-collector on main as the structure template: the file split, pure seeded rules, server-safe metadata, `GameDefinition`, store reporting and tests proving the server limits. Games never import one another.
- Make state once in Scene's lazy `useState` initializer with `createRun(randomSeed())`. One default-priority `useRunFrame` maps `useInput().current` into a per-run step input (`readStepInput`), calls `step(run, dt * 1000, stepInput)` (rules take milliseconds, the store's `frameMs`) and reports store actions/events. Visual callbacks read the resulting state; no per-frame React state. Core priorities guarantee simulation before camera and visuals regardless of mount order; no first-child Simulation convention is needed.
- Reuse `useGameTime`, `useInput` (`moveX`, `pressed`, `jumpPressed`), store, audio, `useFittedView` + `followFocus` + `CameraRig`, `useSafeArea(selector)`, `<Model fallback={...}>`, `<DynamicInstancedModel fallbackParts>`, `SHARED_ASSETS`, `core/render`, `core/math` and `core/limits`. Generic helpers belong in core; ask Claude if another is needed. No local clock hook, camera fitter, safe-area measurement, instancing writer or score-cap function. Rules draw with core `rngNext` from two `RngState` objects made once in `generateTower`: `{ s: seed >>> 0 }` for physics/layout and `{ s: (seed ^ 0x9e3779b9) >>> 0 }` for decoration (no closures, no per-entity streams). Not used: `sweptAabbXZ` (ground-plane boxes; Tower's one-way tops are vertical crossings on x/y, solved analytically) and `createRng`.
- Tower adds an analytic one-way platform jump, a carried-remainder integer-ms rules clock, a reachable permanent route, optional collapsing detours, unique height-band coins and bounded recycled pools. Do not copy warehouse collision, battery effects, layouts or camera numbers. Rules timing belongs to gameplay; purely decorative animation uses the core visual clock.
- Two core follow-up 2 patterns to copy: every moving or recycled pool is a `<DynamicInstancedModel>` with `fallbackParts` (no static instancing, no spot snapshots on recycling); and the end of a run stays animated through the result delay by drawing pure poses of rules time plus visual time (`posedMs`), because `useRunFrame` stops when the run ends.

## Concept

The shared Play50 runner climbs a bright toy tower. Static and horizontally moving platforms form a permanent route; orange crumbling side platforms offer different launch positions. Every 8 m, a broad flagged checkpoint provides a safe place to stop and a coin to collect. Height earns points once, so dropping and climbing the same ledges cannot farm score.

The camera rises with the highest position reached and never follows a fall downward. Falling through the bottom of its play column ends with `end("lose")`. Checkpoints are rest ledges, **not respawns**: no lives, teleports or height reset. That preserves the climbing risk and one simple height/clock proof. The tower continues until a fall or the shell's 30-minute cap (`"timeup"`); there is no finish bonus or `"win"`.

## Controls

Matches `meta.controls` (scheme `"platformer"`): keyboard "A/D or Left/Right to move; Space, W or Up to jump", touch "Joystick + Jump button, or swipe up".

The simulation `useRunFrame` reads `useInput().current` once per frame and follows the core pressed-vs-swipe rule (`core/README.md` "Input events"): `pressed` already carries swipes, so every move comes from `pressed` (or held axes), and `input.swipe` is never read.

| Intent | Read from | Never read for it |
|---|---|---|
| Run left/right | Held `moveX` (A/D, arrows, the analog joystick's x), clamped to [-1, 1]. If `moveX` is 0 this frame and exactly one of `pressed.left` / `pressed.right` is set, this frame uses -1 / +1: a key tapped and released between two frames moves the runner for that one frame (3·dt m, at most 0.15 m at the 50 ms cap) instead of being lost. A horizontal canvas swipe arrives the same way and nudges the same one frame (touch players run with the joystick). | `swipe`; `pressed` while the axis is held (no extra speed, and an opposite tap does not reverse it) |
| Jump | One edge per frame: `jumpPressed \|\| pressed.up`, that is Space, the touch Jump button, a new Up/W keydown, or an upward canvas swipe (which `pressed.up` already includes). Two sources in one frame are still one edge and one buffer entry. | `swipe` (reading it as well would make every swipe a second jump request), held `jump`, `moveY` (pushing the joystick up never jumps) |
| Nothing | `moveY`, `pressed.down` (no drop-through), `tap`, `action`, `actionPressed`, `pointer` | |

- Pure `readStepInput(input, out)` in `rules.ts` does this mapping into one `StepInput { moveX, jumpEdge }` made per run and rewritten every frame (no allocation). `step` sees only `StepInput`, so tests feed edges directly and also test the mapping. `pressed` is read field by field, never kept. Canvas swipes need no `touchControls` entry (InputProvider always reads them), so the definition keeps `["joystick", "jump"]`. Motion is on the x/y plane at z = 0; right is +x on both aspects.
- Held jump never auto-jumps and there is no variable-height jump or double jump.
- Ground and air both set horizontal velocity to `3 * moveX` m/s (the mapped `StepInput.moveX`) immediately (air-control multiplier 1.0); releasing stops horizontal input motion. A moving support adds its horizontal carry only while grounded. Esc/P, hidden tab and blur use shell pause.
- A jump press is buffered for 120 ms of simulation time. Walking off a ledge leaves 100 ms of coyote time. The first accepted jump consumes both buffer and the single grounded/coyote permission; that permission rearms only on a valid descending landing. Track edges during the opening hold, but discard them at its end so held Space cannot launch automatically.

## Constants

World units are metres. Heights/collision coordinates use metres; generation samples heights in integer millimetres.

| Name | Value / invariant |
|---|---|
| Gravity / jump velocity | 10 m/s² downward / +4 m/s |
| Jump apex / time to apex | 0.8 m / 400 ms |
| Horizontal speed / air control | 3 m/s / 1.0 |
| Minimum interval between accepted launches | 400 ms; no platform/buffer/coyote path can bypass it |
| Coyote / jump buffer | 100 / 120 ms, inclusive deadline |
| Runner collision / draw size | Foot point plus horizontal half-width 0.22; visual 0.55 m high, 0.44 wide, 0.40 deep, floor-pivoted in `assets.ts` |
| Ordinary platform | 1.4 wide × 0.6 deep × 0.16 thick; one-way top |
| Required height steps | 0.45, 0.50 or 0.55; consecutive base-centre shift ≤1.0 |
| Required platform base centres | x in [-1.0, 1.0], on a 0.1 grid |
| Moving platform | Horizontal only, ±0.20 m triangular travel, period 2000 ms, speed ≤0.40 m/s; no vertical lifts |
| Crumbling spur | 0.8 wide, only beside a static required platform; centre shift 1.2 m to side `-sign(x)` (seeded left/right when x = 0); full x-range inside [-1.10, 1.10], clear of checkpoint props; 800 ms warning starts at the runner's first contact with it (a landing on it, a landing on its parent that overlaps it, or walking onto it from its parent), then collision is removed and the debris (drawn only) falls vertically with gravity 6 m/s², capped at 6 m/s |
| Checkpoint | Every 8 m / 16 required steps; permanent 4.4-wide ledge centred at x = 0 |
| Coin density / pickup | One unique coin at each positive 8 m band, radius 0.30; pickup reach 0.52 and feet-height gate described below |
| Height / coin points | 10 per whole metre of new maximum foot height / 25 per coin |
| Opening protected hold | 350 ms of simulation time; feet stay on start ledge, no jump, falling or points |
| Earliest loss result | 3000 ms of integer simulation time; an earlier fall latches failure and waits without further motion or awards |
| Result delay | Core default 800 ms (`resultDelayMs` not set): after any end, scene and HUD stay up, the fall and debris keep animating, then the result panel |
| Rising bottom / look-ahead | `viewBottomY = maxHeight - 2.0`; fit up to `maxHeight + 4.0` |
| World play bounds | Runner centre x clamped to ±1.98, z = 0; camera guard box x = ±2.3, z = ±0.6 |
| Run cap / maximum frame | 1800000 ms shell duration / core `MAX_FRAME_DT = 0.05` s |
| Pools | 32 required platforms, 16 optional spurs, 4 coins, 4 flags, 8 decorative tower sections |

The 350 ms hold is a brief "Left/right, then Jump" introduction on a broad ledge. Horizontal practice is allowed but cannot leave it or award points. After unlock, play starts immediately. To meet the server's 3 s minimum, a fall before `run.timeMs >= 3000` sets `pendingLose`, clears jump permission/buffer and freezes gameplay state/awards; only the simulation clock continues until the loss result is allowed. This records the failure when it happens and adds no recovery or invulnerability. Pause freezes that wait too. The runner's fall is drawn during the wait, and the core 800 ms result delay follows the deferred `end("lose")` ("End of the run on screen").

## Rules

### Seed, generation and recycled pools

- On each Scene mount, outside rules, the lazy initializer draws a fresh unsigned 32-bit seed with core `randomSeed()`, then passes it to `createRun(seed)`. Retry/restart remount by `runId`. Strict Mode may evaluate the initializer twice; it has no external effects, and only committed state is used. Asset seed 5050 is unrelated to the gameplay seed.
- Rules use core `rngNext(state)` (**mulberry32**, the same sequence as `createRng(seed)` without a closure) on `{ s: seed >>> 0 }`. Integer weighted draws use `floor(rngNext(state) * totalWeight)` and cumulative integer weights. Required ordinary platforms use static:8, moving:2; checkpoints and the first two steps are always static. Optional-spur presence uses absent:1, present:1, subject to reachability. A separate stream `(seed ^ 0x9e3779b9) >>> 0` supplies decoration, so visual choices cannot alter physics.
- Each 8 m block has eight pairs of height steps. Uniformly choose a pair from (450, 550), (500, 500), (550, 450) mm: each pair totals 1000 mm, and the 16th platform is exactly the next checkpoint height. Choose each x from the grid candidates satisfying bounds and neighbour distance; at step 16 use x = 0. Since all base centres are within ±1.0, that final shift also satisfies the bound. A missing candidate uses the previous base centre; validation must still pass, with no retry-until-lucky loop.
- Precompute 451 blocks (7216 required descriptors, through 3608 m) on mount. This exceeds the proof's maximum reachable height plus look-ahead. Reward/flag descriptors are needed only for reachable bands 1..450; the last checkpoint is a guard beyond the play window, so its props need no extra next block. All descriptors, optional slots, absolute IDs and phases are fixed for the seed. Rules take this seed; no random draws or layout allocations occur in the frame loop.
- An optional crumbling spur is at the same height as an **ordinary static** required platform, never a moving platform or checkpoint. Set `side = -sign(x)`; at x = 0 draw left/right with seeded integer weights 1:1. Its centre is `x + side * 1.2`. Admit only when within ±1.2 and within 1.0 of the next required base centre; otherwise omit it. Static attachment guarantees a physical gap `1.2 - (1.4/2 + 0.8/2) = 0.10 m`, without moving-platform travel closing it. Never replace a required platform. There is at most one spur per pair; it offers another launch position, no extra height or coin.
- Generate the next block's step 1 before placing the checkpoint's coin/flag. Choose the side opposite that step's base x (seeded integer choice if x = 0): coin x = `side * 1.50`, flag x = `side * 1.90`. Coin radius is 0.30; flag's full visible x half-width is at most 0.20 including its pennant. Reserve the first slab's full possible x-range `[nextX - 0.90, nextX + 0.90]` (0.70 half-width + 0.20 travel), even when static. For nextX ≥0 and side = -1, the coin occupies [-1.80, -1.20] and flag [-2.10, -1.70], both left of the slab's minimum ≥-0.90; mirror for nextX <0. This gives at least 0.30 m coin clearance and 0.80 m flag clearance for every seed. Both stay on the 4.4 m checkpoint ledge, away from the next block's first slab. Validate these ranges, not just prop centres.
- **Spur/checkpoint clearance:** additionally require the spur's full visible/collision x-range `[spurX - 0.40, spurX + 0.40]` to lie inside **[-1.10, 1.10]**; equivalently `|spurX| ≤ 0.70`. This keeps at least **0.10 m** from either possible checkpoint coin range (nearest edge at ±1.20) and **0.60 m** from either flag range (nearest edge at ±1.70), including beside the next block's first slab. Omit a failing optional candidate; do not move the coin/flag, required platform or spur to force it in. The seeded x = 0 side choices both produce centres ±1.20 and are therefore omitted. Apply this clearance for every spur, even when the nearby checkpoint props are hidden or already collected. The warning rock turns the slab only about its own long (x) axis, and falling debris stays at the same x with no spin/side drift, so neither can cross a coin/flag's x-range later. This only reduces optional spurs; the permanent required route/reachability proof is unchanged.
- Pools hold descriptors in the 10 m moving window `maxHeight - 4` through `maxHeight + 6`. Recycle only after a slot is below the loss boundary and is neither a contact nor a pending collision target. Write transforms/kind/absolute ID into existing slots; never remount/dispose geometry during play (the render pools only read the slots, "Rendering"). Monotone descriptor cursors and coin IDs prevent respawning rewards. This window needs fewer than 32 required platforms and 16 spurs; 4 coins/flags cover its 8 m bands. Candidate collision data may extend beyond the visible column; the render pools hide copies outside its y bounds, and a flag until its full 0.8 m height fits. Detached/unused slots have no collision.

### Kinematic physics and reachability

No Rapier. Between events use the analytic arc `y(t) = y0 + 4t - 5t²`, `vy(t) = 4 - 10t`, horizontal input velocity capped as above. One-way collision accepts only a descending crossing of a platform top from above, with horizontal footprint overlap (more than 0 m) at the crossing time. Jumping through its underside never lands. Solve the crossing within each integration slice, use interpolated platform x, and take the earliest crossing; tops crossed at the same instant (only a parent and its spur share a height) all become contacts, in absolute-ID order. Never snap feet upward beyond the analytic trajectory's maximum. Core `sweptAabbXZ` tests ground-plane boxes, not this vertical one-way crossing, so the crossing stays analytic in `rules.ts`.

**Contacts and support.** The runner is grounded while its feet stand at a top's height after a descending landing, or by walking at that height. Its **contacts** are every collidable top at exactly the feet height (heights are integer millimetres, so the compare is exact) whose x-range overlaps the footprint `[x - 0.22, x + 0.22]` by more than 0 m; edges that only touch (overlap 0) are not a contact. Contacts are evaluated at every landing and at the end of every ≤1 ms slice. Required heights are all distinct and a spur shares only its static parent's height, so the runner has at most two contacts, and when it has two both are static: horizontal carry comes from the single contact when that one moves, and no tie rule is needed. The runner stays grounded while it has any contact. Losing the last one, by walking off or by a collapse, starts the 100 ms coyote window at that ms. The footprint (0.44 m) is wider than the parent/spur gap (0.10 m), so the runner **walks between a parent and its spur at the same height without leaving the ground or landing**: with the spur on side `s`, the spur is a contact while `s·(x - parentX) > 0.58` and the parent while `s·(x - parentX) < 0.92`, so the 0.34 m band between touches both.

Physics consumes integer-ms slices no longer than 1 ms, with swept top crossings, not a discrete end-position overlap. Resolve the collision within a slice, finish its remaining motion once, and process a buffered launch only at an integer-ms boundary. Use absolute integer deadlines for coyote, buffer, warning and minimum launch interval. This avoids tunnelling and frame-size-dependent jump height; it does not mean rendering 1000 times a second.

**Every required next platform is reachable:** apex is `4² / (2 * 10) = 0.8`, 0.25 above the highest allowed rise. The descending arrival for rise d is `t(d) = (4 + sqrt(16 - 20d)) / 10`. For d in [0.45, 0.55], t is 0.623607–0.664575 s. Even when both platforms move to their worst extremes, centre separation is at most `1.0 + 0.2 + 0.2 = 1.4`. Available horizontal travel at the earliest landing is `3 * 0.623607 = 1.870820`, a **0.470820 m** margin. From the departure centre, a chosen constant velocity of at most `1.4 / 0.623607 = 2.245` reaches any arrival phase; keyboard players can move at full speed, then release. The platform's usable full-support half-width is `0.7 - 0.22 = 0.48`, covering 1 ms input discretization (≤0.0034 m). Reaching the centre is stronger than merely overlapping an edge.

Moving platforms stay at a fixed height, have no disappearance deadline, and can be waited on. Their full travel range is already in the proof. They carry horizontally, never boost a jump vertically. An admitted spur is at most `1.0 + 0.2 = 1.2 m` from the next required centre including its motion; returning to its static counterpart is a same-height jump (0.8 s, 2.4 m horizontal reach versus 1.2 m separation). Its 800 ms warning exceeds the ≤665 ms next-platform flight. Collapse may punish waiting, but cannot erase the required route or its safe departure surface. Walking onto a spur from its parent changes none of this: the parent stays a contact across the whole 0.34 m straddle band, and every runner position with spur contact (`0.58 < s·(x - parentX) < 1.82`) is at most 0.90 m (300 ms at 3 m/s) from regaining the parent, so even walking to the spur's far edge and back (413 + 300 = 713 ms) fits inside the 800 ms; only waiting is punished, and a jump works from either surface. Falling visuals have no collision after warning expiry.

**Warning trigger.** A spur changes `INTACT → WARNING` in the **first ≤1 ms slice in which it becomes one of the runner's contacts** ("Contacts and support"), and records `warnStartMs` = that slice's end ms (an integer) and the absolute deadline **`warnStartMs + 800`**. In frame terms that is the first `step` in which the runner's support includes the spur; the Scene and the HUD see `WARNING` in that same frame. It covers all three ways the spur can come under the feet:

1. a descending landing on the spur;
2. a descending landing on the parent whose footprint already overlaps the spur (both become contacts at once);
3. **walking from the parent onto the spur at the same height**, with no landing and no airtime: the first slice whose end puts `s·(x - parentX)` above 0.58 m.

Generation, entering the view, proximity (standing on the parent with `s·(x - parentX)` ≤ 0.58, footprint edge at most touching the spur's edge), jumping over it, passing up through it from below or touching its underside do not start the warning. Leaving it (walking back onto the parent, jumping, falling) and contacting it again by any of the three ways never reset or extend the deadline; it keeps running while the runner is elsewhere. At a slice boundary with `timeMs ≥ warnStartMs + 800`, remove collision before processing a simultaneous landing, contact or jump, and set `collapseMs` = that ms (the debris starts falling, drawn only). A runner still straddling then keeps the parent as its contact: it stays grounded, with no coyote window and no change to its jump permission. A runner whose only contact was the spur loses support and gets the 100 ms coyote window from `collapseMs`. Pause freezes simulation time and therefore the remaining warning; recycling into a new absolute spur ID restores `INTACT`, while the same ID never rearms.

### Simulation timing and frame order

**Every gameplay timer, physics motion, moving-platform phase, crumble warning and collapse, pending-loss wait and rising camera anchor advances only from the simulation `useRunFrame` dt passed to `rules.ts step(run, dtMs, stepInput)`.** The two drawn-only motions (falling debris and the runner's loss fall) are pure poses of that rules time, extended by visual time only once the run is over (below). `step` takes **milliseconds**: the Scene passes `dt * 1000`, exactly the store's `frameMs`, at most 50 (passing seconds would run the game about 1000 times too slow). The countdown transition includes only its counted residual play time. No `setTimeout`, `performance.now`, `Date.now`, tween completion callbacks or stored `state.clock.elapsedTime`.

Keep a carried fractional ms remainder: `step` adds `dtMs` (capped at 50) to the remainder, takes its whole milliseconds, keep the fraction in [0, 1), and increment integer `run.timeMs` by those whole ms. Do not round each frame or discard its fraction. This rules clock never runs ahead of cumulative counted play dt and trails it by less than 1 ms. Advance physics and gameplay deadlines from these consumed ms. dt ≤0 or non-finite does nothing. A jump edge is enqueued once per frame, never per substep; carry remaining time through hold/collapse/landing boundaries once. Paused redraw/refit cannot consume the remainder.

Use default-priority `useRunFrame`, without an override. `FRAME_PRIORITY` orders input (-2) → run clock (-1) → game time (-0.75) → simulation (-0.5) → CameraRig (-0.25) → plain `useFrame` visuals (0). This holds regardless of child/mount order. Pure tests drive the same order with `advanceRunClock(store, delta)` and `playedFrameDt(store.getState())`.

Visual callbacks use core `useGameTime()`: coin spin/ambient bobbing use `now`, decorative easing uses `delta` (0 paused), and play-bound animation/optional runner clips use `play` or the current rules pose. `now` also advances outside playing, so it must never trigger a launch, collapse, pickup or end. Everything collision-bearing (runner root while alive, static and moving slabs at `slabX(desc, run.timeMs)`, intact and warning spurs with their warning progress) reads rules state only, so it holds still whenever the rules stop (pause, the end). The drawn-only motions read **`posedMs(run, vis, phase, now)`** (phase from `useArcadeStore.getState()`, `now` from `useGameTime()`): `run.timeMs` while the phase is not `"over"`, then `run.timeMs + 1000 * (now - vis.endNow)`. `vis` is a visual-only scratch object made once per Scene mount; `vis.endNow` is the `now` latched by whichever visual callback first sees phase `"over"`. Game time advances (-0.75) before every visual (0), so every callback of a frame gets the same value whatever their order, and the first `"over"` frame continues exactly from `run.timeMs`. Visual easing cannot change collisions or finish a gameplay event. No visual callback advances rules. CameraRig handles visual easing after the monotone simulation anchor has updated.

### Height, coins and end

- `maxHeight` is the greatest foot y reached, measured from the start ledge y = 0. Use the analytic peak inside a slice too, not only its final y. Award +10 when each previously unawarded integer metre is crossed. Descending, landing, checkpoint visits and camera motion do not award height.
- The coin for band k has absolute ID k, eligibility height `8 * k`, and is drawn 0.30 m above that checkpoint at x = ±1.50, on the side chosen above. It can be collected only once, with feet at/above `8 * k`, the runner's pickup centre `(x, footY + 0.275, 0)` within 0.52 of its draw position, and `maxHeight >= 8 * k`. A big mesh/pickup radius cannot award the next band's coin early. At most `floor(maxHeight / 8)` coins can ever count; missed coins below the camera are lost. Checkpoints give no points.
- After physics/peak/coin events, set `viewBottomY = maxHeight - 2.0`. The simulation camera anchor F = `maxHeight` never decreases. A descending feet crossing below that bottom latches loss once, after reporting score/height up to the crossing, and records `run.loss = { atMs, x, footY, vy }` at the crossing (the pose the fall is drawn from); stop further gameplay at that event, including the rest of the frame. If `run.timeMs < 3000`, advance only the integer clock until 3000 before `end("lose")`; otherwise end immediately. The boundary is the bottom of the fitted **play column**, independent of viewport, not a device-dependent screen ray. Draw a faint danger strip there and hide tower geometry below it.
- Report score changes with imported core `capScore(rawScore, store.elapsedMs, towerClimbMeta.scoring)` as a safety net; the proof requires it to leave every reachable score unchanged. Shell time-up runs before Simulation and wins same-frame ties, with no later pickups; the store already holds the capped score from its latest award. GameShell submits the store score and default rounded `elapsedMs`; no `finalScore` override, API calls or game-local persistence. Coin sound is `playSfx("pickup")`; an accepted launch is `playSfx("jump")`; falling loss is `playSfx("hit")` at the crossing (not at a deferred `end`), once each event.

### End of the run on screen (the 800 ms result delay)

- Tower keeps the core default: `resultDelayMs` is not set, so GameShell submits the score the moment the run ends (`"lose"` or `"timeup"`; there is no `"win"`) and keeps the scene and the HUD up for 800 ms of rendered frames before the result panel (`core/README.md` "After the run"). During the delay the phase is already `"over"`: `useRunFrame` no longer runs, so `step` is never called, input is not read, the store would ignore score/stat changes, and the rules state stays exactly as the end left it.
- The end therefore animates in visuals only, from pure poses in `rules.ts` evaluated at `posedMs` ("Simulation timing and frame order"):
  - **The fall (`"lose"`).** `lossFall(run.loss, ms)` continues the runner's own arc from the crossing: the same x, feet at `footY + vy·τ - 5τ²` with `τ = (ms - atMs) / 1000` and `vy ≤ 0` there, no collision. The runner is drawn through the danger strip and hidden once its head is 1.0 m below it (feet 1.55 m below). The drop is at least `5τ²`, so that takes at most `sqrt(1.55 / 5) = 0.557 s`, inside the 800 ms: every fall is seen in full before the panel. An early fall (crossing before 3000 ms) draws the same pose during its wait, where `run.timeMs` still advances and pause freezes it; after the deferred `end("lose")` the delay adds its 800 ms (an early fall at 1000 ms ends the run at 3000 ms of rules time and shows the panel 800 rendered ms later).
  - **Debris.** A spur that collapsed before the end keeps dropping (`debrisDrop(ms - collapseMs)`) at its own x through the delay, and is hidden once below the strip.
  - **Everything else holds.** Slabs, moving slabs, intact and warning spurs, coin positions and a living runner keep their final rules pose, so after `"timeup"` a runner on a moving slab stays on it. Coin spin and bob keep using `now`. F, the follow target and the loss line do not change, so CameraRig holds still.
- No sound plays during the delay. The poses are functions of time, so any `resultDelayMs` from 0 to 5000 would also work; 800 needs no override. Score and `elapsedMs` are fixed at the end, so the delay changes nothing in the proof.

### Server limits and why they hold (the proof)

Metadata and WP config (tightened 2026-10-07 from `maxScore: 50000`, `maxPointsPerSec: 100`, which accepted about 10 times the honest rate): `kind: "points"`, `maxScore: 19000`, `base: 0`, `maxPointsPerSec: 11`, `minDurationMs: 3000`, `maxDurationMs: 1800000`, `unitLabel: "pts"`, `display: "int"`. Server checks integer score, `score <= 19000`, duration D in [3000, 1800000] ms and `score * 1000 <= 11 * D`.

1. **Counted clock and short start.** `dt = frameMs / 1000` includes the counted play remainder of the countdown-transition frame: there is no untimed simulation frame. Pause advances neither clock. Integer rules time is ≤ cumulative counted dt. Let D be GameShell's `Math.round(elapsedMs)` and t = D/1000; rounding down costs at most 0.5 ms. Retain **50 ms only as conservative slack**, not a core behaviour or test premise. After the 350 ms hold, climbing time U is bounded by `U <= max(0, t + 0.0505 - 0.350) = max(0, t - 0.2995)`. Actual core timing has the tighter bound `max(0, t - 0.3495)`. An early fall freezes awards and defers its result until integer rules time ≥3000, which implies submitted D ≥3000. Time-up has D =1800000. Quit does not submit. The core result delay starts after `end()`: GameShell has already submitted, `elapsedMs` no longer advances and score changes are ignored, so the delay changes neither S nor D.
2. **Maximum climb rate for any input/seed** (replaces the old launch-guard bound `H <= 0.8 + 2U`, 26.25 pts/s, which is about 2.6 times looser than the game allows).
   - (a) A launch needs permission, and only a descending landing rearms it (or the start ledge). A launch starts no higher than the surface the runner stands on: spurs are at their parent's height, a coyote launch starts lower, and nothing carries the runner upward or boosts the jump. Waiting, walking off, walking between a parent and its spur or taking a collapsing spur cannot help, and neither can the input mapping: every source (`jumpPressed`, `pressed.up`, a swipe inside it) only requests a launch, and the `pressed` nudge keeps `|moveX| ≤ 1`.
   - (b) The apex is 0.8 m (`V_JUMP² / 2G`). Each pair of steps rises exactly 1 m (a first rise of 0.45, 0.5 or 0.55 and the rest), so any two consecutive rises add up to at least 0.9 m (1.0 inside a pair, at least 0.45 + 0.45 across pairs). A launch from step i therefore lands at most on step i+1: one required step per launch, never a skip.
   - (c) vy0 is always 4, so the time from launch to landing on a top d higher is fixed: `t(d) = (4 + sqrt(16 - 20d)) / 10`, 664.575 / 644.949 / 623.607 ms for d = 0.45 / 0.50 / 0.55. The next launch comes at or after the landing. Every 1 m pair therefore costs at least **1288.182 ms** (450 + 550 in either order; 500 + 500 costs 1289.898).
   - (d) Height H ≥ M needs a launch from step 2M−1 and then a further rise of 1 − d1 in the air (time `(4 - sqrt(16 - 20(1 - d1))) / 10`). So whole metre M is reached no earlier than `earliest(M) = 0.35 + 1.2881819 (M − 1) + 0.7590317 = 1.2881819 M − 0.1791502` s (the first metre at 1.109 s). The score is `S <= 10M + 25 floor(M/8)`, counting each coin as early as possible (the moment H reaches 8k).
3. **Rate for every prefix.** (e) The largest S/t over all M is at M = 8: 105 / 10.1263 = **10.369 pts/s**, or 105 / 10.0758 = 10.421 with the 50.5 ms slack of step 1. Both are below 11 for every M, so `S * 1000 <= 11 * D` holds and `capScore` stays a no-op on every reachable award; the smallest absolute gap is at the first metre (cap 12 against 10 points at 1.109 s), so the cap is a no-op even before 3 s. The sustained maximum is 13.125 pts/m / 1.2881819 s/m = 10.189 pts/s, so 11 is the smallest integer that works (the server casts `max_pps` with `(int)`, and 10 is below the 10.189 asymptote; 10 would need base ≥ ~1050, which would accept ~1150 points at 10 s instead of 110). During the hold S = 0. Frozen early-loss scores stay valid as their duration increases. This covers every input/seed, same-step awards, idle input and terminal result. Multiply by 1000 for the integer server inequality.
4. **Absolute cap.** (f) By 1800 s, `M <= floor((1800 + 0.0505 + 0.17915) / 1.2881819) = 1397`, so `S <= 13970 + 25 * 174 = 18320` (`MAX_THEORETICAL_SCORE`), 3.71% under `maxScore` 19000. A run cannot reach 19000 before the 30-minute cap, or at that cap. The precomputed 3608 m route far exceeds this H plus the 6 m pool look-ahead; `BLOCKS` stays 451 because shrinking it would change the RNG draws for spurs, coins and decoration and break the pinned-layout tests.

Margins: 11 pts/s is 6.1% above the steepest honest S/t (10.369 at M = 8), 5.6% above it with the 50.5 ms slack and 8.0% above the sustained 10.189. 19000 is 3.71% above the proven 18320 (3.77% above the measured 18310). 3000 ms is the earliest honest end (`MIN_LOSS_MS`) and 1800000 ms is `DURATION_MS`. The best a forger can post drops from 50000 (at a claimed 500 s) to 19000 at a claimed 1727273 ms or more; the accepted ceiling at 3 s drops from 300 to 33 points, at 60 s from 6000 to 660.

Measured with a throwaway smart bot (not committed; it buffers a jump every frame, aims each landing at `slabX` at the arrival time and takes coins in flight): 64 full 30-minute runs (16 seeds × 8.3 / 16.7 / 50 / random 1–50 ms frames) and 3 seeds at 1 ms frames all ended in time-up with **18310** (1396 m, 174 coins); 4800 runs of 60 s (600 seeds × 4 frame patterns, with and without 5% input noise) never broke the analytic bound and never fell. Best ratio 10.3622 pts/s at 10133 ms (analytic 10126 ms for 105). The test's centre-landing bot is slower: 583.67 pts/min = 9.73 pts/s.
5. **Core safety net and terminal duration.** Import `capScore(score, durationMs, rules)` and `withinServerLimits(score, durationMs, rules)` from `core/limits.ts`; pass raw store `elapsedMs`, which those helpers round like GameShell. No local cap implementation or `finalScore` override. Tests require the cap to be a no-op on every reachable award/terminal result and every terminal result to pass `withinServerLimits`; a clamp must not hide broken physics/density. Exercise countdown carry, duration rounding and carried rules remainder against the real store. The proof's extra 50 ms remains slack only. An idle runner stays on the start checkpoint and times out at 1800000 ms with **0 points**.

## Edge cases

- Pause mid-jump freezes velocity, coyote/buffer deadlines, moving supports, camera anchor and integer remainder. Resume consumes only new simulation dt; no catch-up, duplicate jump edge or renderer-clock reset effect.
- The first contact starts the warning once, whether by landing on the spur, landing on the parent while overlapping it, or walking onto it from the parent with no landing; leaving and contacting it again (walking back and forth across the 0.34 m straddle band, relanding) never refreshes its 800 ms. Pause while standing on or away from that warning platform preserves the remaining time exactly; the visual cannot fall while collision stays behind. A resumed warning expires only after its remaining simulation ms. A collapse at a jump boundary removes collision first; a runner still straddling stays grounded on the parent (no coyote), a runner on the spur alone gets coyote from `collapseMs`, and an already valid coyote permission/buffer may still launch, once. Spur x-range remains clear of checkpoint coin/flag through warning and vertical fall.
- Input: a Left/Right key tapped and released between two frames moves the runner one frame; held keys plus `pressed` add no speed. A swipe up jumps once (from `pressed.up`), never twice, and a swipe together with Space or Jump in the same frame is still one edge. Pushing the joystick up never jumps; `pressed.down` and taps do nothing.
- Result delay: after `end()` there is no step, no input and no sound; the loss fall and debris keep animating from `posedMs`, everything collision-bearing holds still, and the HUD stays up until the panel. An early fall shows its fall during the 3 s wait, then the 800 ms delay. A frame that both ends the run and starts the first `"over"` visuals draws the end pose itself (`posedMs` = `run.timeMs`), with no jump.
- Fast downward crossings use the swept top test. Touching an underside/side does not restore jump permission. A landing/buffer within one frame carries remaining time once, and the 400 ms launch guard always holds. Walking off does not create repeated coyote jumps.
- If a new peak raises the bottom past the runner after a fall, report earned score then latch loss once. Before 3000 ms, freeze gameplay/awards and wait using only simulation time; pause/restart honours the pending state. No checkpoint teleport or recovery during that wait. Time-up takes precedence over same-frame collision/pickup; score and duration match the shell's ended state.
- Restart/retry rebuilds seed, descriptors, pools, deadlines, remainder, score and camera anchor; consumed coins never leak into the next run. Mount/suspense/loading time does not start rules time.
- Rotate/resize refits the same state, preserving left/right and loss height. Only the shell's coarse portrait policy owns orientation pause/overlay; fine-pointer landscape has no game-local gate. An unlisted or broken runner GLB uses its explicit `<HumanoidModel fallback>` element (the animated stand-in), and every pool (flag included) its `fallbackParts`, with no separate clone/failure-check component.
